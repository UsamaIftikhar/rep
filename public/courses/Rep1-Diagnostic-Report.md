# Rep 1 — Full Diagnostic Report

*Prepared from a complete audit of the Bubble.io editor: every page, every data type, every workflow, every installed plugin, and every settings tab. Compiled September 10, 2026.*

## What Rep 1 is, in one paragraph

Rep 1 is a Bubble.io no-code web application that connects student-athletes with college and international recruiters. It combines an athlete recruiting profile builder with combine-testing stats, a six-class "Student Academy" curriculum with progress tracking, an AI-branded mock interview practice tool, a recruiter search and shortlist tool, a full admin console, a multi-tier subscription and billing system (athlete, recruiter, and parent-pays-for-athlete plans), and a semi-independent sister brand, Elite Pacific Sports Recruiting, aimed at Australian athletes with its own $75/mo access tier and its own admin login.

## Tech stack

The app is built entirely in Bubble.io (no custom code repository — this diagnostic came from reading the live editor, not a codebase). It currently runs on Bubble's **Starter Web Plan at $32/mo** (175K workload units/month, 50GB file storage, 1 app editor seat, 2 days of server logs), and is presently 13 days into its trial, with the card on file set to be charged automatically when the trial ends around September 23. The web app is marked **LIVE**, but no custom domain has been connected — it is still being served from Bubble's default subdomain, and consequently the domain-dependent email and TLS settings are also unconfigured.

Five plugins are installed: **Stripe** (payments), the **OpenAI Assistant API** plugin (installed, but — as detailed below — never actually called from any workflow), the **API Connector** (present but holding only one empty, unconfigured draft call to a placeholder "test.com" endpoint — safe to delete), **Slick Slideshow** (powers the rotating athlete banner carousel on the Elite Pacific page), and **Multiselect Dropdown** (a UI form plugin). There's also a linked third-party privacy scanner, Flusk, reachable from the Data → Privacy tab, which the app is not currently required to use but could run for an independent security pass.

## Data model

The app has 16 custom data types plus Bubble's built-in User type, backed by 15 option sets (enumerations) for things like account status, subscription status, sport, position, and interview status. The core objects are: **User** (the single largest type — holds the athlete's profile fields directly, like GPA, height, weight, sport, position, school, role, profile visibility, plus links out to a subscription and a parent user), **Athlete** (a separate, smaller type with its own Name/School/Sport/Country/Recruiting-Tier fields that looks like an earlier or parallel athlete record — worth checking whether it's still used anywhere, since the profile page reads athlete data from User, not from Athlete), **AcademyClass** and **AcademyProgress** (the six-class curriculum and each athlete's per-class status), **CombineStat** and **Photo** (an athlete's testing numbers and uploaded media), **Event**, **Blog Post**, and **Banner** (site content), **ProfileView** and **ShortlistEntry** (recruiter engagement tracking), **Subscription** and **BillingHistory** (billing records, including a real `stripe_subscription_id` field), **PlatformMetric** (feeds the admin dashboard's total-users/active-subscriptions/searches counters), and **Interview Question** and **Interview Session** (the mock interview feature).

One structural issue surfaced here: **there are two separate data types both named "Interview Session"** — one whose athlete-link field is called `Athlete`, the other whose field is called `Athlete User`. Both have "privacy rules applied." This is almost certainly a duplicate created at some point during development, and it's part of why the privacy-rule checker below is confused about which "Interview Session" it means. This should be cleaned up — consolidated into one type — before the privacy rule is finalized, otherwise you risk configuring the rule on the wrong (possibly unused) copy.

## What actually works today

Authentication, role-based navigation (Athlete / Recruiter / Parent / Admin / Elite Pacific Admin), the athlete profile editor, the six-class academy with admin-side content management, the recruiter search and shortlist tool, the admin console's user/subscription/class/testing-data management, the blog and events content sections, and the core Stripe-backed self-serve checkout for athletes and recruiters are all implemented with real, working workflows wired to real data. The admin console alone has 18 distinct workflows covering full CRUD on users, classes, subscriptions, and testing data — it's genuinely complete.

## What's not finished — the important part

Three things stand out as significant gaps, in addition to the three outstanding items already in Bubble's own issue checker.

**The Mock AI Interview feature doesn't call AI at all.** I checked every workflow tied to it, plus the app's single Backend Workflow, and there is no step anywhere that calls the OpenAI Assistant API plugin (which is installed but otherwise unused in the entire app). "Start a new interview session" just creates a session record and shows the question flow; "Submit an interview answer" just saves the raw answer text and resets the input for the next question. The Interview Question data type has AI Feedback and Score fields, and the results screen has UI for "Overall Score" and "Overall Feedback," but nothing in the app ever populates them. As it stands today, this feature collects athletes' interview answers as plain text and never grades or responds to them — it's a UI shell around the intended feature, not a working one.

**Payment processing is inconsistent across the four checkout paths.** The athlete self-serve checkout and the recruiter self-serve checkout on the `subscription` page both correctly call "Charge the current user via Stripe" as their first step before creating any database records — those are real. But the "Register athlete and process parent payment" flow (the parent-pays-for-their-athlete option) and the entire Elite Pacific $75/mo checkout on the `elite_pacific_recruiting` page skip Stripe entirely: they go straight to creating a Subscription record and a BillingHistory record marked "Paid," with the billing amount hardcoded, regardless of whether any money actually changed hands. Separately, canceling a subscription and updating a payment method both only change a database field — neither one calls Stripe to actually cancel the underlying subscription or update the card on file, so a real Stripe subscription (where one exists) would keep renewing even after a user "cancels" it in the app. On top of that, all four checkout popups collect the card number, expiry, and CVC through plain text input fields rather than Stripe's dedicated tokenizing card element, which is worth a security review before this goes anywhere near real card numbers — that's the kind of thing that normally needs to be resolved before a payments feature can be considered launch-ready.

**Three issues remain in Bubble's own checker**, unchanged from when I last reported: the app needs a real Google Geocode API key added under Settings → API (this requires your own Google Cloud credential — not something I can generate for you); and two data-privacy rules — "athlete's own data" on Interview Question and on Interview Session — currently have empty conditions, which the checker flags because an empty condition is ambiguous rather than because it's necessarily wrong. From digging into the data model, I can now tell you what the fix likely looks like: Interview Session (at least the one with the `Athlete` field) can probably use "Current User = This Interview Session's Athlete," while Interview Question has no direct athlete field of its own, so its rule would need to go through the session, e.g. "Current User = This Interview Question's Session's Athlete" (adjusted for whichever field name the Session lookup actually uses on Interview Question). I still want your explicit sign-off before setting either one, both because getting a privacy rule wrong can either leak another athlete's interview data or lock the athlete out of their own, and because of the duplicate Interview Session type noted above — we should resolve that duplication first so we know which type the rule is really meant to protect.

A few smaller items round out the list: the SEO and Open Graph settings under Settings → SEO and metatags are still Bubble's own unedited defaults ("The most powerful no-code platform," site name "Bubble") rather than anything about Rep 1, which matters as soon as a link gets shared or the site gets indexed. The academy page's copy is hardcoded to "6-Class Academy" and "The 6 Classes," but Bubble's own AI agent panel (left over in the editor from earlier work) shows a suggested list of seven class topics — Financial Literacy, Leadership, Marketing Playbook, Personal Branding, Community Engagement, Behavioral Analysis, and "Australia to America" — worth reconciling since seven doesn't match "six." No custom domain is set up yet. Two-factor authentication is available but requires upgrading off the Starter plan to actually turn on. And the app's trial ends around September 23, after which the card on file will be charged for the Starter plan automatically — worth knowing before that date arrives.

## Suggested plan

Given all of this, I'd frame the next steps as three tracks: first, decide and confirm the two privacy-rule conditions (and clean up the duplicate Interview Session type) so the issue checker can finally hit zero; second, decide what to do about the Mock AI Interview feature and the two non-Stripe payment paths, since both are places where the UI currently promises something the backend doesn't deliver; third, handle the pre-launch housekeeping — Google Geocode key, custom domain, SEO metadata, and the academy content mismatch — whenever you're ready to move this toward a real launch rather than a trial build.
